What this skill is

atlas-pov-app is one of five cooperating skills that make up an Atlas proof-of-value build. Where atlas-pov-seed plants the data and atlas-pov-narrative tells the story, this skill owns the thing the customer actually clicks through: the Next.js app itself. It encodes a set of hard-won, non-obvious decisions — a Voyage embedding call that silently breaks without one flag, a keyword-search leg that returns nothing if you reuse the wrong query string, an LLM response shape that hides the real answer behind a reasoning step — so that every engagement doesn't relearn them from scratch.

Before it writes a line of code

It reads engagement.config.js for the tenant field, primary collection, search/embedding paths, index names, and LLM gateway settings — then checks engagementType to decide which of the two tracks below applies.

03Core library files

db.ts — ping-based reconnect

A cached client that pings before reuse. Skip the ping and a server restart costs every subsequent request a 30-second hang before it notices the connection is dead.

export async function getDb(): Promise<Db> {
  if (db) {
    try { await db.command({ ping: 1 }); return db; }
    catch { client = null; db = null; }
  }
  client = new MongoClient(uri);
  await client.connect();
  db = client.db(dbName);
  return db;
}

voyage.ts — the dimension flag that must not be dropped

output_dimension: 1024 is not optional. Omit it and query vectors come back at a different width than the ones already stored, and $vectorSearch fails on a dimension mismatch — one of the more confusing failure modes to debug cold.

body: JSON.stringify({ input: [text], model: 'voyage-4-large', output_dimension: 1024 })

selfQuery.ts — LLM query decomposition

Built only when rankFusion is in headlineFeatures. This is the most architecturally significant file in the whole skill: it calls the LLM before embedding, splitting free text into a clean semanticQuery (entity names stripped, safe to embed), typed hard filters, and a one-line explanation.

Three rules the system prompt must enforce

1. Named entities (drugs, SKUs) are stripped from the embedded text — they belong in the keyword leg, not the vector.
2. Numeric measurements are hard filters, not identity fields the LLM might fold into something like age.
3. The literal word "json" appears in the LLM input whenever json_object format mode is used.

Entity spelling variants (e.g. "BRAF V600E" vs. "BRAF mutated") are normalized via a domainMap read from config — never hardcoded — so free-form LLM output still matches what's actually stored for an $in filter.

04API routes

Every route is wrapped in try/catch — without it, Next.js returns an empty 500 body and the client sees a bare Unexpected end of JSON input instead of a real error. Only the routes matching headlineFeatures get built.

/api/vector-search — the centerpiece

Runs the self-query LLM step, embeds the cleaned semantic query, then fuses two $rankFusion legs. The rule that matters most here: the keyword leg searches the raw input text (drug names intact), never the stripped semanticQuery — otherwise the two legs stop disagreeing and the compare view has nothing to show.

$rankFusion: {
  input: { pipelines: {
    vector:  [{ $vectorSearch: { index, path: EMBEDDING_PATH, queryVector: semanticVector, ... } }],
    keyword: [{ $search: { index, compound: { should: terms.map(t => ({ text: { query: t, path, synonyms: 'domain_synonyms' } })), minimumShouldMatch: 1 } }}],
  }},
  combination: { weights: { vector: vw, keyword: kw } },
}

Keyword terms use compound.should, not a single multi-word text query — Atlas Search's text operator ANDs terms by default and returns nothing once they span different fields.

/api/search

Atlas Search text query with synonym-aware highlighting, built only if search is listed.

/api/analytics

Promise.all across several aggregation pipelines, built only if analytics is listed.

/api/chat — RAG

Embed the question → $vectorSearch retrieval → build a context string from the enriched fields (not just summary text) → call the LLM gateway. Gateway response parsing needs its own care: the first item in a Grove/OpenAI Responses API output array is often a reasoning step with empty content, so the answer is found with output.findLast(o => o.type==='message' && o.content?.length > 0).

05UI components

A fixed component vocabulary, styled entirely in the green brand palette — never black or generic gray text.

QueryPanel

Shows the executed MongoDB pipeline on every search/vector page, with the raw embedding array swapped for a placeholder before display.

LimitSlider

Label stacked above the track so it fills sidebar width; max 100 for RAG, 50 for plain search.

WeightSlider

rankFusion only. One bar, keyword left / vector right, live percentage pills on both ends.

CompareView

rankFusion only. Three columns — vector-only, keyword-only, hybrid — with presence badges. The single most effective demo surface in the app.

Every hybrid-search page ships three pre-verified demo presets: a query where keyword wins, one where vector wins, and one where only the hybrid combination captures both — each auto-configuring the weight slider and enabling compare mode on click.

06Fast validation endpoint

Any page with pre-loaded examples gets a lightweight GET route that checks each example actually returns results before showing it — so a demo never opens on a preset query that silently returns zero rows.

GET /api/.../validate?text=...
→ embeds text, runs a 1-result $vectorSearch, returns { hasResults: boolean }

Alternate track — Queryable Encryption / CSFLE

When engagement.config.js sets engagementType: 'encryption', Steps 1–6 above are skipped entirely — there is no headlineFeatures fork on this track, and no Search/Vector/$rankFusion/chat/LLM code exists at all.

Default track

Search · Vector · Hybrid · RAG

  1. Feature-gated by headlineFeatures
  2. Voyage embeddings + LLM gateway
  3. Self-query decomposition for hybrid search
  4. Compare view is the demo centerpiece
Encryption track

Queryable Encryption / CSFLE

  1. Fixed feature set — no gating
  2. Two lazily-initialized MongoClients: encrypted & raw
  3. Consumes key maps the seed workstream already built — never re-derives them
  4. /admin side-by-side view is the demo centerpiece

Two client singletons, never hand-rolled:

getEncryptedClient(mode)

autoEncryption with the field/schema map built from the shared buildFieldMaps.js and the seed workstream's .keyids.json — same data keys the stored ciphertext actually used.

getRawClient()

A plain client with no auto-encryption — the simulated DB-admin view. Used only to prove it structurally cannot decrypt anything.

Three API routes plus one deliberate rejection: POST /api/customers (transparent encrypt), GET /api/customers (decrypted list), GET /api/customers/lookup (equality query on a field validated against piiFields — anything else is a 400, which is itself a demo point), and GET /api/admin/raw, which renders ciphertext explicitly as { kind: 'ciphertext', bsonSubtype: 6, ... } so it can never be mistaken for a plain string.

Gotcha: .env.local doesn't inherit

A Next.js app scaffolded into its own subdirectory does not auto-load a repo-root .env.local. The encryption bootstrap module resolves and parses the shared root file explicitly, rather than letting a second, divergent copy get created inside the app.

Common mistakes this skill exists to prevent

  • No try/catch on a route → empty 500 body, client crashes with Unexpected end of JSON input.
  • Singleton DB client without a ping check → 30-second timeout on the first request after any server restart.
  • Multi-word text query in the keyword leg → Atlas Search ANDs terms by default; use compound.should with minimumShouldMatch: 1 instead.
  • semanticQuery reused in the keyword leg → drug names already stripped, keyword leg returns nothing, compare mode shows no divergence.
  • Grove/OpenAI response parsed naively → output[0] is a reasoning step with empty content; use findLast to find the real message.
  • Missing output_dimension: 1024 → query vectors come back 2048-dim against 1024-dim stored vectors; $vectorSearch errors on mismatch.
